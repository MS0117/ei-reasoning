## 1. Arm과 iteration

| arm | config | operator | loss | iterations |
|---|---|---|---|---|
| **Ours** | `l5_staged_dpo_s3.yaml` | staged_bridge_sft (stage-2 DPO) | cliff objective S3 (ρ=0.3, guard on) | 3 |
| **LSPO** | `l5_lspo.yaml` | lora_sft (gold y\* adapter) | 동일 (operator만 다름) | 3 |
| **Gold-in-loop** | `l5_gold_inloop.yaml` | gold_text (y\* 원문을 cliff 행으로) | 현행 | 3 |
| **RFT / ReST-EM** | `l5_rft.yaml` | 없음 (solved-only) | 현행 | 3 |
| **Gold SFT** | `l5_gold_sft.yaml` | 없음 (offline y\* 전량) | 현행 | 1 |
| **Bridge-in-loop** | `l5_bridge_inloop.yaml` | bridge_text (bridge z+ 원문을 cliff 행으로, LoRA 없음) | 현행 | 3 |

- looped arm은 **K=3 동일**.
- 데이터 **확정: `data/mixes/openr1_mix6k_qwen3-4b-2507.jsonl`** (6,000문항, cliff 2,730 = 45.5%).
  8k의 층화 strict subset이라 분포가 동일하고, 8k 대비 비용 −22.7%인데 검정력은 영향받지
  않는다(headline이 별도 holdout에서 나오므로). holdout은 8k의
  `openr1_mix8k_..._cliff_holdout.jsonl`(300 cliff) 하나를 **전 arm이 공유**하며, 부분집합과
  disjoint임을 확인했다.
- **loss는 arm마다 다르다** — 이것이 의도적 설계다:

  | arm | loss | 이유 |
  |---|---|---|
  | Ours, LSPO | S3 (ρ=0.3, guard, `m_per_batch: auto`) | 두 arm의 차이를 operator 하나로 고정 |
  | Gold-in-loop, RFT, Gold SFT, Bridge-in-loop | 현행 (`cliff.enabled: false`) | baseline은 표준 SFT로 읽는다 |

  결과적으로 **Ours vs Gold-in-loop는 데이터원(on-policy 궤적 vs gold 원문)과 loss를 동시에
  바꾼다** — 단일 변수 대조가 아니다. 필요하면 `scripts/fork_run.py`로 gold-in-loop의 S3
  변형을 rollout/improve 재사용 + train부터만 다시 돌려 (~비용 13%) 붙일 수 있다.
  RFT에 S3를 켜서는 안 된다: cliff 행이 0이면 L_C=0이라 loss가 `0.7·L_S`로 균일 축소되어
  학습률을 0.7배 한 것과 같아진다.
- **Bridge-in-loop**(2026-08-31 추가) = STaR rationalization: 정답 필터만 걸고 **leakage 필터는
  끈다**(원형). 실측(L2 freeze): kept bridge의 35.5%가 "reference solution" 류 문구를 포함, y\*
  축어 복사 0.4%, LoRA 재샘플 후 0.2% — 비율은 `improve/stats.json:n_bridge_leak_phrasing_reported`로
  보고만 한다. bridge 성공률(L3 79%)이 conversion(46%)보다 높아 cliff 행이 있는 문항이 ~1.7배
  많다 — arm이 재는 것의 일부이며 `n_questions_bridged`를 arm별로 병기한다.
- 공통 고정: `rollout.n=8 @16384`, `solved_keep_max=4/shortest`, `filter.max_per_question=2`,
  `train`(lr 1e-5, epochs 2, batch 32, `init_from: base`, zero2, region_weights).
  테스트가 5개 config의 이 shape 일치를 강제한다(`tests/test_build_gold_sft.py`).

## 2. Headline은 loop 밖에서 측정한다

**loop의 `eval` stage는 추적용이다.** iteration마다 holdout 300 × k=4 @16384(greedy off)와
벤치 카나리아(aime24 n=8, math500_hard n=4)를 찍어 **곡선**을 그린다. 논문 수치가 아니다.

**Headline은 최종 iteration ckpt에 대한 사후 re-roll이다** — L3에서 검증된 측정 경로 그대로:

```bash
# arm마다 1회 (최종 ckpt)
.venv/bin/python scripts/cliff_reroll.py --run-dir runs/<arm> \
    --qids-file holdout --n 32 --passes 1 --model-path runs/<arm>/iter_2/ckpt \
    --out runs/<arm>/headline

# base floor: 전 arm이 공유하는 1회 (2 pass = floor + paired-null 검정)
.venv/bin/python scripts/cliff_reroll.py --run-dir runs/<any-arm> \
    --qids-file holdout --n 32 --passes 2 --out runs/floor_holdout

.venv/bin/python scripts/attractor_mass.py \
    --verdicts runs/floor_holdout/pass_0/verdicts.jsonl runs/floor_holdout/pass_1/verdicts.jsonl \
    --compare runs/<arm>/headline/pass_0/verdicts.jsonl \
    --out runs/<arm>/attractor_holdout_compare.json
```

- **지표**: Δattractor mass(주 지표), Δavg@32, ≥1정답 coverage, Δp_top2, 오답 종류 수.
  비교는 **문항별 paired**, 검정은 양측 sign test — L3 §3-1 정의 그대로.
- **검정력**: L3 power table에서 176문항×32로 attractor 2pp를 power 0.9에 검출.
  holdout 300문항은 이를 상회한다.
- **왜 loop 밖인가**: (a) reroll은 `rollout.max_tokens`(16384)로 돌아 정답 censoring이 없다,
  (b) 매 iteration 300×17을 찍으면 iteration당 ~10h로 전체의 10%를 추적에 태운다,
  (c) config hash와 무관하게 아무 ckpt에나 사후 실행 가능하다.
- **최종 iteration 고정**: dev-argmax로 iteration을 고르지 않는다. K=3의 마지막 ckpt가 headline.
  전 iteration 곡선은 부록에 전량 공개한다.

## 2-1. 코드 리비전 고정

**5개 arm은 동일한 코드 리비전으로 실행한다.** vLLM 풀은 배치 구성이 커널 수치를
바꾸고 temperature 샘플링에서 시퀀스가 갈라지므로, 샤딩·GPU 수·풀 크기가 다르면
같은 seed·같은 config라도 다른 표본이 나온다(engine.py 문서: 1-GPU vs 2-GPU에서
0/160 일치). 2026-08-29 실측: `max_loras`와 샤딩만 바꾼 재실행에서 improve
conversion 52 → 48, 문항 단위로는 27↔23 양방향(McNemar p=0.672).

따라서:

- arm 간 비교(논문의 본체)는 유효하다 — 전부 같은 코드·같은 데이터·같은 예산.
- **L3나 이전 smoke의 점추정치를 L5 점추정치와 같은 표에 병기하지 않는다.**
  결론은 이월되지만 소수점은 이월되지 않는다.
- 결론이 표본 재추출에 흔들리지 않는다는 근거는 L3가 이미 측정해 두었다:
  base pass0 vs pass1(같은 절차, 다른 표본) Δattractor **0.0pp (p=0.78)**,
  Δavg@32 −0.04pp (p=0.89). S3의 −11.0pp는 그 노이즈보다 한 자릿수 크다.
- 작은 n의 operator 지표(conversion 등)는 위 실측대로 수 % 흔들린다. 그 숫자를
  단독으로 인용할 때는 arm 간 차이로만 읽고, 절대값에 의미를 두지 않는다.

### 4-1. `m_per_batch: auto` — 구제 궤적 커버리지

sampler는 epoch 길이를 **solved 풀**로 정한다(`n_win = n_solved // fill`, [train.py:178]).
따라서 cliff 추출 횟수 `n_win × m_C`는 **improved 행 수와 무관**하고, 그 비율이 과추출이냐
과소추출이냐는 우연이다. L3와 L5는 정반대 쪽에 있다:

```
L3 S3         solved 5366 / cliff  118  → n_win 173, m_C=1  → 행당 1.47회 (과추출, 주석이 예상한 경우)
LSPO iter0    solved  526 / cliff   61  → n_win  16, m_C=1  → 커버  26%   (실측)
LSPO iter1    solved 1237 / cliff  110  → n_win  39, m_C=1  → 커버  35%   (실측)
D2 staged     solved  194 / cliff  153  → n_win   6, m_C=1  → 커버   4%   (실측)
6k 본안 iter0  solved ~5724 / cliff ~780 → n_win 184, m_C=1  → 커버  24%   (추정)
```

L5 mix가 cliff를 12.6배 과대표집하므로 **구제 궤적의 3/4가 학습에 들어가지 못한다.** 게다가
추출 횟수가 solved 행 수로만 정해지므로 **cliff 행을 많이 만든 arm일수록 커버율이 낮아지는
역선택**이 생겨 arm 간 비교까지 왜곡된다.

`auto`는 `n_win × m_C ≥ cliff 행`을 만족하는 최소 m_C를 sampler 생성 시 푼다(fill이 m_C에
따라 변하므로 스캔). 위 다섯 경우 모두 커버 100%가 되고, **L3 비율에서는 1로 수렴**해 검증된
설정을 건드리지 않는다. ρ=0.3은 불변이므로 cliff의 총 gradient 비중은 그대로이고, 그 30%를
몇 행이 나눠 갖느냐만 바뀐다.

부수 효과: `per_question_norm`은 m_C=1에서 **무의미했다**(1/n_q가 window 분모와 정확히 상쇄).
m_C ≥ 2에서 비로소 작동해 문항당 dose를 균등화한다. 학습 로그에
`m_c=4(cliff coverage 100%)`로 기록된다.

**유지하기로 한 것**: `rollout/improve.max_tokens=16384`(12288은 정답 손실 0이지만 절감 5~8%뿐이고,
학습된 정책의 길이 드리프트 위험 + passrate 스윕의 cliff 라벨 기준과 불일치),
`improve.n=16`(축소는 conversion 손실 직결 — probe 후 재검토).
